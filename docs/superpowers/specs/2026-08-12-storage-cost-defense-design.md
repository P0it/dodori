# 스토리지 비용 방어선 — 누수 차단 + 성장 상한

작성일: 2026-08-12

## 문제

**도돌이는 수익화하지 않는다.** 2026-08-04 스펙(`2026-08-04-photo-pipeline-cost-design.md`)은
커플당 100장 쿼터를 "무료/유료 경계선이자 결제 유도 지점"으로 규정했지만, 그 전제를 폐기한다.

폐기 이유는 지불 모수다. 쿼터 같은 **사용량 게이트는 상위 몇 %의 헤비 유저에게만 걸린다.**
대부분의 커플은 평생 100장을 못 채우므로 과금 대상이 아니고, 채우는 소수는 1년쯤 지난
뒤에야 도달하는데 그때는 활동량도 지출 의향도 이미 내려간 뒤다. 게다가 커플앱은 이별이
곧 이탈이라 LTV가 짧다. 즉 이 구조는 "가장 아끼는 유저에게만 청구서를 보내면서 총액은
얼마 안 되는" 형태다.

수익화를 뺀 뒤 남는 목표는 하나다 — **청구서가 예측 가능한 상한 안에 머무는 것.** 동시에
서비스를 열어 사람들이 쓰게 하고 싶다. 따라서 필요한 것은 결제가 아니라 **유저가 늘어도
비용이 선형 이상으로 튀지 않는 방어선**이다.

쿼터(`couples.photo_quota`)는 남긴다. 다만 성격이 바뀐다 — 결제 유도 지점이 아니라
**순수한 비용 방어선**이다. `couples.plan` 컬럼은 쓰이지 않는 채로 남는다(제거하지 않는다.
지우는 마이그레이션이 이득 없이 위험만 만든다).

### 전제 — 포함분은 도돌이 전용이 아니다

Supabase Pro 구독은 **조직 단위**이고, 포함분(스토리지 100GB · egress 250GB)도 조직 전체가
공유한다. 프로젝트별 할당이 아니다. 도돌이는 여러 프로젝트를 한 계정에 모은 조직 안에
들어가므로, **포함분 전체를 도돌이의 예산으로 볼 수 없다.**

Spend Cap도 조직 단위다. 따라서 도돌이가 포함분을 다 먹으면 정지되는 것은 도돌이만이
아니라 **그 계정의 모든 프로젝트**다. 이 스펙이 막으려는 최악의 시나리오는 "도돌이가
죽는다"가 아니라 "도돌이 때문에 전부 죽는다"이다.

부수 사항으로, 한 조직에 프로젝트를 여러 개 두면 프로젝트마다 compute 요금이 따로 붙는다
(Pro의 compute 크레딧은 대체로 첫 프로젝트 몫이다). 이는 도돌이 코드로 막을 수 있는 것이
아니라 계정 설계의 문제이므로 전제로만 적는다. 요금 세부는 변동이 잦으니 실제 청구 전에
콘솔에서 확인한다.

## 현황 조사 — 이미 막힌 것과 새는 것

### 이미 잘 되어 있는 것

- **egress** — 서명 URL 24시간 캐시(`src/api/signCache.ts`의 `SIGN_TTL_SEC`) + 업로드 시
  `Cache-Control: 31536000`(`PHOTO_CACHE_SEC`) 조합이 재다운로드를 없앤다. 경로가 uuid라
  같은 주소의 내용이 바뀌지 않으므로 1년 캐시가 안전하다
- **서버 이미지 변환** — 신규 사진은 온디바이스 렌디션 2종이라 변환을 타지 않는다
- **개별 삭제** — 사진·게시물·스토리·트랙 커버 삭제가 전부 `storagePathsFor()`를 경유해
  `_360`까지 함께 지운다 (`photos.ts:415`, `posts.ts:161`, `stories.ts:203`, `tracks.ts:319`)
- **버킷은 둘뿐** — `photos`, `avatars`. 다른 업로드 경로가 없다

### 누수 1 — 쿼터 트리거가 파일을 못 막는다

`uploadPhotos`(`src/api/photos.ts:349`)는 스토리지에 파일 2개를 **먼저** 올리고 그 다음
`photos` insert를 한다. 쿼터 트리거는 insert의 `before insert`에 걸려 있으므로, 한도에
도달한 커플이 업로드를 시도하면 **파일은 스토리지에 남고 DB 행만 없다.** 롤백(`remove`)도
없다. 재시도할수록 스토리지가 무한히 자란다 — 방어선 정면에 뚫린 구멍이다.

### 누수 2 — 아바타는 쿼터 밖이고 영원히 쌓인다

`uploadAvatar`(`src/api/photos.ts:191`)는 매번 새 uuid 경로(`{uid}/{uuid}.jpg`)로 올리고
이전 파일을 지우지 않는다. `photos` 테이블에 행이 생기지 않으므로 쿼터 트리거와 무관하다.
프로필 사진을 20번 바꾸면 파일이 20개 남는다. `avatars`는 public 버킷이라 서명 없이
egress도 나간다.

### 누수 3 — 커플이 사라져도 파일은 남는다

`photos.couple_id`가 `on delete cascade`라 커플이 지워지면 DB 행은 사라지지만
**스토리지 객체는 안 지워진다.** 지금은 탈퇴·해체 기능 자체가 없어 잠재적이지만, 앱스토어가
계정 삭제를 요구하므로 곧 필요해진다. 커플앱은 이탈률이 높아 장기적으로 여기가 제일 크게
샌다 — 헤어진 커플의 사진이 영원히 요금을 먹는다.

### 누수 4 — 커플 수에는 상한이 없다

커플당 100장은 유계지만 커플 수는 무한이다. 위 전제에 따라, 이 방향으로 터지면 조직의
모든 프로젝트가 함께 정지된다.

## 결정 — 네 겹

| 겹 | 무엇 | 무엇을 막나 |
|---|---|---|
| 1 | 커플당 쿼터 (기존) | 커플 하나의 사용량 상한 |
| 2 | 업로드 순서 뒤집기 + 아바타 폴더 정리 | 누수 1·2를 발생 지점에서 |
| 3 | `sweep-storage` cron | 누수 1·2·3이 놓친 고아 파일 전부 |
| 4 | 배정 몫 + 신규 커플 생성 차단 | 누수 4 — 조직 동반 정지 |

## 1. 업로드 순서 뒤집기

현재: `path 생성 → 렌디션 렌더 → 파일 업로드 ×2 → photos insert(트리거 검사)`

변경: `path 생성 → 렌디션 렌더 → photos insert(트리거 검사) → 파일 업로드 ×2`

렌디션 렌더가 insert보다 앞서야 하는 이유는 `width`/`height`가 렌더 결과(`main.width`,
`main.height`)에서 나오기 때문이다. 렌더는 기기 안에서만 일어나므로 순서를 앞에 둬도 비용이
없다.

쿼터에 걸리면 insert가 예외로 거부되고 **파일은 아예 안 올라간다.** 반대 방향 실패(insert는
됐는데 파일 업로드가 실패)는 방금 만든 행을 `delete`로 지운다 — 이쪽 롤백이 훨씬 싸다.
행만 있고 파일이 없으면 깨진 이미지가 뜨므로 롤백은 생략하지 않는다.

여러 장 루프 중간에 실패하면 앞서 성공한 장들은 이미 커밋된 상태로 남는다. 이는 현재 동작과
같으므로 변경하지 않는다.

## 2. 아바타 폴더 정리

`uploadAvatar`가 새 파일을 올린 뒤 `{uid}/` 폴더를 `list()`해서 **방금 올린 파일만 남기고
나머지를 `remove()`한다.**

"`profiles.avatar_url`에서 이전 경로를 역산해 하나만 지우는" 방식보다 이쪽이 나은 이유는
이미 쌓인 과거 누적분까지 한 번에 청소되기 때문이다. 호출부가 이전 URL을 넘길 필요도 없어
시그니처가 그대로다.

정리 실패는 업로드를 실패시키지 않는다 — 아바타는 바뀌었는데 청소만 못 한 상태는
`sweep-storage`가 나중에 덮는다.

## 3. `sweep-storage` — 고아 파일 청소 cron

주 1회, 두 버킷을 훑어 **DB가 참조하지 않는 객체 중 생성 후 24시간이 지난 것**을 삭제한다.

- 24시간 유예는 **업로드 중인 파일을 지우지 않기 위해서다.** 이 유예가 없으면 누수 1을
  고치는 순서 뒤집기와 경합해 방금 올린 사진을 지울 수 있다
- `photos` 버킷의 참조 집합은 `photos.storage_path` 전체
- `avatars` 버킷의 참조 집합은 `profiles.avatar_url`에서 추출한 경로

### 함정 — `_360` 정규화를 빠뜨리면 목록 렌디션을 전부 지운다

DB에는 본체 경로(`{uuid}.jpg`)만 있고 `_360`은 `renditionPath()`가 만드는 **파생 경로라
테이블에 없다.** 대조 전에 정규화하지 않으면 모든 목록 렌디션이 고아로 판정돼 삭제된다 —
앱 전체의 썸네일이 사라진다. 대조 시 `_360.jpg` → `.jpg` 치환을 반드시 먼저 한다.

### 왜 Edge Function인가

`storage.objects`의 행을 SQL로 지워도 **실제 오브젝트 파일은 남는다.** 삭제는 Storage
API(`.remove()`)를 거쳐야 하므로 순수 pg_cron으로는 불가능하다. 기존
`20260713000006_cron_sync_holidays.sql`의 패턴(vault에서 `project_url`·`service_role_key`를
읽어 `net.http_post`)을 그대로 따른다. vault 시크릿이 없으면 `raise notice` 후 스킵하는
동작도 동일하다.

한 번에 지우는 개수에 상한을 둔다(1000개). 실행이 길어져 타임아웃으로 통째로 실패하는
것보다, 남은 분량을 다음 주에 마저 지우는 쪽이 안전하다.

## 4. 배정 몫과 신규 커플 생성 차단

### 배정 몫

도돌이 몫을 **스토리지 70GB**로 정한다(조직 포함분 100GB의 70%). egress 몫은 180GB로
보되 코드로 강제하지 않는다 — 아래 "왜 스토리지만 강제하나" 참고.

100%를 배정하지 않는 이유는 방어선이 곧 Spend Cap 자체가 되어 완충이 사라지기 때문이다.
같은 조직의 다른 프로젝트들은 DB를 많이 쓰지 않으므로 도돌이가 대부분을 가져가되, 30%는
다른 프로젝트와 안전 여유로 남긴다.

참고 규모: 쿼터를 꽉 채운 커플이 18.5MB이므로 70GB는 약 3,800쌍이다. 실제 평균 사용량은
쿼터보다 훨씬 낮으므로 수용 커플 수는 이보다 여유 있다.

### 값은 DB에 둔다

`couples.photo_quota`가 그랬듯 **코드 변경 없이 조정할 수 있어야 한다.** 단일 행 테이블
`app_limits`에 둔다.

| 컬럼 | 기본값 | 의미 |
|---|---|---|
| `storage_budget_bytes` | 70GB | 도돌이에 배정한 스토리지 몫 |
| `storage_used_bytes` | 0 | `sweep-storage`가 매주 갱신하는 실측값 |
| `signups_blocked` | false | 신규 커플 생성 차단 여부 |
| `updated_at` | — | 마지막 갱신 시각 |

### 2단계 차단

`sweep-storage`가 총량을 잰 뒤 `app_limits`를 갱신한다.

- **80% 도달** — 차단하지 않는다. `storage_stats.budget_pct`로 읽히므로 별도 플래그를 두지
  않는다. 이 구간의 목적은 "닿기 전에 알아차리는 것"뿐이다
- **100% 도달** — `signups_blocked = true`. 신규 커플 생성만 막는다

**기존 커플은 전부 정상 동작한다** — 사진 열람, 업로드(개인 쿼터 안에서), 모든 기능이
그대로다. 막히는 것은 새 커플이 생기는 것뿐이다.

해제는 수동이다. 자동 해제를 넣지 않는 이유는, 한도에 닿았다는 것은 사람이 판단할 일
(몫을 늘릴지, 정리를 할지, 이전할지)이 생겼다는 뜻이기 때문이다. 자동으로 풀리면 그 판단이
영영 미뤄진다.

### 강제 지점

`create_couple(p_invite_code)` RPC(`20260708000003_create_couple_rpc.sql:9`)가 커플이
생기는 **유일한 지점**이다. 함수 첫머리에서 `app_limits.signups_blocked`를 읽어 참이면
예외로 거부한다. `claim-invite` Edge Function은 이미 만들어진 커플에 합류하는 경로이므로
막지 않는다 — 한쪽이 이미 가입한 커플은 완성될 수 있어야 한다.

클라이언트는 이 예외를 받아 "지금은 새로 시작할 수 없어요" 안내를 띄운다.

### 왜 스토리지만 강제하나

egress는 **누적값이 아니라 월별 유량**이라 프로젝트 안에서 정확히 재기 어렵고, 신규 가입을
막아도 기존 유저의 열람량에 따라 그대로 튄다. 즉 차단이 잘 듣지 않는 축이다. 대신 egress는
`storage_stats`에서 추세만 보고, 위험 신호가 오면 사람이 판단한다(이전 검토 등).

스토리지는 단조 증가라 차단이 곧바로 듣는다. 그래서 강제는 스토리지에만 건다.

## 5. `storage_stats` — 주간 스냅샷

`sweep-storage`가 같은 실행에서 집계를 한 행 남긴다. 화면은 만들지 않는다 — SQL Editor로 본다.

| 컬럼 | 의미 |
|---|---|
| `taken_at` | 스냅샷 시각 |
| `couples_total` | 커플 수 |
| `photos_total` | 사진 행 수 |
| `bytes_total` | `storage.objects`의 `metadata->>'size'` 합 (버킷별) |
| `avg_photos_per_couple` | 커플당 평균 |
| `p90_photos_per_couple` | 커플당 90분위 — 평균만 보면 헤비 유저 꼬리가 안 보인다 |
| `swept_objects` | 이번 실행에서 지운 고아 개수 |
| `budget_pct` | 배정 몫 대비 사용률 |

`swept_objects`가 계속 0이 아니면 어딘가에서 고아가 새로 생기고 있다는 신호다 — 청소만
하고 넘어가지 않도록 이 값을 함께 남긴다.

스냅샷이 몇 주 쌓이면 증가율에서 "현 추세로 배정 몫에 언제 닿는가"가 계산된다.

## 6. 스토리지 이전 판단 기준 (문서만)

코드는 건드리지 않는다. 아래 조건 중 하나가 관측되면 Cloudflare R2 / AWS S3 이전을 검토한다.

- 스토리지가 **배정 몫(70GB)의 80%를 넘을 때**
- 월 egress가 **배정 몫(180GB)의 80%를 넘을 때**

R2는 egress가 무료고 저장이 $0.015/GB라 원가 구조가 근본적으로 내려간다. 다만 서명·접근
제어를 RLS 밖에서 직접 짜야 하므로 공사가 크다. **지금 하지 않는 이유는 단가가 문제가
아니라 뚫린 구멍이 문제이기 때문이다** — 구멍을 막지 않은 채 옮기면 더 싼 곳에서 똑같이 샌다.
