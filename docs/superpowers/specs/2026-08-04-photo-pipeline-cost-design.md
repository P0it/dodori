# 사진 파이프라인 재구성 — 요금 상한 설계

작성일: 2026-08-04

## 문제

실서비스 개방 시 서버 비용이 통제 없이 늘어나는 게 두렵다. 청구서가 예측 가능한 상한 안에
머물러야 한다.

조사 결과 **"데이터를 기기에 저장하고 프리미엄에만 클라우드를 제공"하는 방향은 도돌이에
맞지 않는다.** 도돌이의 모든 테이블(`events`·`photos`·`posts`·`stories`·`topic_votes`·
`game_scores`)은 두 사람이 같이 보는 데이터라, 로컬에만 두면 상대 기기에서 안 보이고 앱의
존재 이유가 사라진다. 무료 티어가 혼자 쓰는 메모장이 되고, 커플 중 한 명이라도 결제하지
않으면 서비스가 성립하지 않는다.

실제 비용은 텍스트가 아니라 **사진(Storage·egress·이미지 변환)**에 몰려 있다. 텍스트
데이터는 커플 수천 쌍이 몇 년 써도 DB 무료 한도(500MB) 안이다.

## 핵심 발견 — 서버 이미지 변환이 Spend Cap을 터뜨린다

Supabase 요금(2026-08 확인):

| 항목 | Free | Pro ($25/월) | 초과 |
|---|---|---|---|
| Storage | 1GB | 100GB | $0.0213/GB |
| Egress | 5GB | 250GB | $0.09/GB |
| Cached Egress | 5GB | 250GB | $0.03/GB |
| **Image Transformations** | **미제공** | **origin image 100장** | **1,000장당 $5** |

현재 `signedThumbUrl()`은 `createSignedUrl(..., { transform })`로 **서버 측 이미지 변환**을
쓴다. 과금 단위는 요청 수가 아니라 그 달에 변환된 원본 이미지 장수다. Pro 무료분이 100장뿐이라
Spend Cap을 켜면(초과 청구 대신 기능 제한) **베타 첫 주에 앱 전체 썸네일이 깨진다.**
Spend Cap을 끄면 사진 10만 장 기준 월 $500이 청구된다.

"$25 고정 상한"과 서버 이미지 변환은 양립할 수 없다. 이 설계의 중심은 이걸 제거하는 것이다.

**현재(Free) 동작도 확인이 필요하다.** Free 플랜에는 이미지 변환이 아예 제공되지 않으므로,
원격 프로젝트에서 `transform` 옵션이 무시되고 **캘린더 124px 자리에도 2048px 원본이 통째로
내려오고 있을 수 있다.** 테스트 사용자가 두 명이라 드러나지 않았을 뿐이며, 사실이라면 Free의
5GB egress를 빠르게 소진한다. 구현 시작 전에 실제 응답 크기를 확인한다.

## 결정

1. **Supabase Pro $25/월, Spend Cap ON** — 청구서가 $25를 넘는 경로를 원천 차단.
   현재는 Free이고 **배포 시점에 Pro로 전환**한다
2. **서버 이미지 변환 폐기** → 업로드 시 기기에서 렌디션 생성
3. **보관 최대본 1080px** — 2048px "원본" 계층 폐기
4. **렌디션 2종** — 1080(본체) + 360(목록). 124(캘린더)는 폐기하고 캘린더도 360을 쓴다
5. **게시물 업로드에 크롭 UI**(핀치줌 + 팬) — 인스타 규격
6. **커플당 사진 100장 쿼터** — DB 트리거로 강제. 무료/유료 경계선이자 결제 유도 지점이다.
   권한 컬럼을 미리 만들어 두되 결제 구현은 이번 범위 밖. 최종 숫자는 베타 실측 후 확정
7. **스토리는 지금처럼 영구 보관** — 만료 삭제 없음

## 1. 렌디션 구조

사진 1장 = 파일 2개.

| 렌디션 | 크기 | 대략 용량 | 쓰는 화면 |
|---|---|---|---|
| 본체 | 장변 1080, JPEG q80 | 150KB | 피드 캐러셀, 스토리 뷰어, 트랙 전체화면 플레이어 |
| 목록 | 장변 360, JPEG q70 | 35KB | 피드 그리드, 앨범 커버, 스토리 그리드, 트랙 격자, 캘린더 칸 |

합계 약 185KB/장 → 100GB에 약 54만 장.

지금도 업로드 시 2048px로 리사이즈해 파일 1개를 올린다(`resizeForUpload`). 실질 변화는
**본체를 2048→1080으로 줄이고 360 파일 1개를 추가**하는 것이다.

360을 유지하는 이유: 격자 화면은 사진 밀도가 가장 높다. 한 화면 30장 기준 1080으로 내려주면
4.5MB, 360이면 1MB다. 35KB를 더 저장해 egress 4.3배를 막는다.

124를 버리는 이유: 캘린더(`tracks.ts:48`) 한 곳에서만 쓰이고 7KB라 용량 이득이 없다. 빼면
사진당 업로드 횟수가 3→2회로 줄어(게시물 10장이면 30→20회) 업로드 체감 속도와 실패 확률이
개선된다. 캘린더는 360을 받아 화면에서 축소해 그리고, `expo-image`가 기기 캐시를 하므로
두 번째 조회부터 egress가 0이다.

### 경로 규칙

```
{couple_id}/{parent_id}/{uuid}.jpg       -- 본체 1080
{couple_id}/{parent_id}/{uuid}_360.jpg   -- 목록 360
```

`signedThumbUrl(path, kind)`은 `transform` 옵션 없이 해당 경로의 서명 URL만 만든다.
`originalUrl()`은 폐기한다 — 본체가 곧 최대본이므로 `track/[id]/player.tsx`도
본체 경로를 쓴다.

### 기존 사진 전환

이미 올라간 사진에는 `_360` 파일이 없다. 백필 대신 폴백으로 처리한다.

- `photos.renditions boolean not null default false` 컬럼 추가
- 신규 업로드만 `true`
- `signedThumbUrl()`은 `renditions=true`면 경로 방식, `false`면 기존 `transform` 방식

현재 실사용이 테스트 2명분이라 기존 사진 수가 Pro 무료분 100장 안이다. 백필 없이 자연 전환된다.

### 삭제 경로

지금은 `storage_path` 하나만 지운다. 렌디션이 생기면 `_360`도 함께 지워야 하며, 누락하면
지운 사진의 파일이 스토리지에 영구히 남는다(고아 파일). 수정 대상 3곳:

- `src/api/photos.ts:246` (사진 개별 삭제)
- `src/api/posts.ts:137` (게시물 삭제)
- `src/api/stories.ts:181` (스토리 삭제)

`renditions=false`인 사진은 본체만 지운다.

## 2. 업로드 크롭 UI

### 프레임 비율

사진 원래 비율을 따르되 범위를 제한한다 — `PostCard.tsx:55`의 표시 클램프와 같은 값이다.

```
ratio = clamp(height / width, 0.5625, 1.25)
```

- 세로 최대 4:5 (1.25) — 인스타 세로 규격
- 가로 최대 16:9 (0.5625)

범위 안에 드는 사진은 잘리지 않는다. 가로로 넓은 풍경 사진도 16:9까지는 그대로 들어간다.
업로드 프레임과 피드 표시 프레임이 정확히 일치하므로 "올릴 때 본 그대로" 피드에 뜬다.

### 동작

- `create-post`에서 고른 사진을 탭하면 크롭 모달이 열린다
- 핀치줌(확대) + 팬(이동)으로 보여줄 영역을 정한다
- 손대지 않으면 **중앙 크롭이 기본값**
- 크롭은 **업로드 시점에 확정해 굽는다** — 갤러리 원본 해상도에서 crop한 뒤 1080으로
  줄이므로 화질 손해가 없고, 표시할 때 줌·좌표를 되계산할 필요가 없다. 진짜 원본은 올린
  사람 폰 갤러리에 남아 있다

### 적용 범위

크롭 UI는 **게시물 업로드에만** 붙인다. 스토리는 9:16 전체화면이고 트랙 사진은 격자 표시라
프레임 개념이 다르다. 두 경로는 비율을 보존한 채 렌디션만 적용한다.

## 3. 커플당 쿼터 + 유료화 자리

### 성격 — 비용 방어가 아니라 결제 유도 지점

**쿼터는 비용을 막는 장치가 아니다.** 비용은 Spend Cap이 이미 $25에서 자르고, 그 위로도
기울기가 완만하다:

| 커플 수 | 스토리지 | egress | Pro 초과 청구 |
|---|---|---|---|
| 5,000쌍 | 93GB | 125GB | $0 |
| 10,000쌍 | 185GB | 250GB | 약 $2 |
| 50,000쌍 | 925GB | 1,250GB | 약 $108 |

(무료 100장 = 18.5MB/쌍, 월 egress 25MB/쌍 가정)

50,000쌍 기준 원가는 커플당 **월 약 3원**이다. 유료 커플이 월 ₩3,000을 내면 스토어 수수료
30%를 떼도 ₩2,100이 남으므로 **유료 한 쌍이 무료 600쌍을 감당한다** — 손익분기 전환율이
0.2% 미만이다.

따라서 한도 숫자는 **"언제 결제 화면을 보여줄 것인가"**라는 수익 질문이다.

### 숫자 — 100장으로 시작

커플 앱의 활동량은 **연애 초기 6개월에 몰린다.** 1년 차가 되면 활동도 결제 의향도 함께
떨어지고, 상당수는 그 전에 헤어진다. **한도는 화력이 남아 있는 구간 안에서 닿아야 한다.**

월 업로드량을 월 10~40장으로 보면 100장은 3~10개월에 도달한다. 폭이 넓은 이유는 실사용
데이터가 두 명분뿐이기 때문이다 — 이 숫자는 추정이다.

**TestFlight 베타에서 "커플당 월 업로드 장수"를 실측한 뒤 스토어 출시 직전에 확정한다.**
트리거가 `couples.photo_quota`를 읽으므로 컬럼 기본값만 바꾸면 된다. 한도는 나중에 올릴
수는 있어도 내릴 수는 없으므로(기존 사용자 반발), 확정 전까지는 추측으로 공개하지 않는다.

### 스키마

`photos`에 `couple_id`가 없어(경로 접두사로만 유도 가능) 컬럼을 추가한다.

- `photos.couple_id uuid not null references public.couples(id)`
- 기존 행 백필: `split_part(storage_path, '/', 1)::uuid`
- `create index photos_couple_idx on public.photos (couple_id)`
- `before insert` 트리거에서 해당 커플의 사진 수가 쿼터 이상이면 예외

권한은 **개인이 아니라 커플에 귀속시킨다.** 스토어 결제는 개인 계정 단위지만 도돌이의
혜택은 두 사람이 함께 받으므로, 나중에 결제를 붙일 때 이 컬럼 값만 바꾸면 되도록 자리를
미리 만든다.

- `couples.plan text not null default 'free'`
- `couples.photo_quota integer not null default 100`

트리거는 상수가 아니라 `couples.photo_quota`를 읽는다. 결제 연동 시 코드 변경 없이
컬럼 값만 올리면 된다.

### 한도 도달 시 동작

**기존 사진은 절대 지우지 않고, 보기도 계속 된다.** 새 업로드만 막는다 — 추억을 담는
앱에서 이미 올린 것이 사라지거나 안 보이게 되는 건 어떤 이유로도 허용하지 않는다.

- 업로드 화면에 잔량 표시 — "사진 62 / 100장"
- 한도 도달 시 안내 문구 — "공간이 가득 찼어요. 곧 더 많은 공간을 제공할 예정이에요"

무료 한도를 좁게 잡으면 **앱스토어 별점 리스크**가 따라온다("몇 장 올렸더니 돈 내래요"
1점 리뷰). 별점은 신규 앱의 노출에 직결되고 되돌릴 수 없으므로 방어책을 함께 넣는다:

1. **사전 고지** — 스토어 소개와 온보딩에 무료 한도를 명시. 나중에 알게 되는 게 아니라
   처음부터 아는 조건이어야 한다
2. **기존 사진 유지** — 위 동작 (열람은 영원히 무료)
3. **낮은 가격** — 월 2~3천 원대. 활동 기간이 짧은 카테고리라 비싼 구독은 팔리지 않는다

전체 사용량은 Supabase 사용량 알림 이메일(70%/90%)로 미리 안다.

### 베타 계측

스토어 출시 전에 한도를 확정하려면 실사용 데이터가 필요하다. 베타 기간 동안 커플별 월
업로드 장수를 집계할 수 있어야 한다. `photos.couple_id`와 `created_at`이 있으므로 별도
계측 코드 없이 SQL 집계로 충분하다 — 구현 시 확인만 한다.

## 4. 코드 배치

CLAUDE.md 의존성 방향(`app/ → components/ → api/·lib/ → theme/·types/`)을 따른다.

| 파일 | 역할 |
|---|---|
| `src/lib/crop.ts` | **순수 함수.** 프레임 비율 클램프, 제스처 상태(scale·tx·ty) → 원본 픽셀 crop rect 변환, 경계 보정. React·RN·Supabase import 없음 |
| `src/lib/__tests__/crop.test.ts` | 단위 테스트 — 비율 클램프, 중앙 기본값, 줌·팬 변환, rect가 이미지 경계를 넘지 않음 |
| `src/components/CropFrame.tsx` | **props-only.** `uri`·`width`·`height`를 받고 `onChange(rect)` 방출. 네트워크·전역상태 없음 |
| `src/app/modals/crop-photo.tsx` | 조합만 — 훅 호출 + 컴포넌트 배치 |
| `src/api/photos.ts` | 렌디션 생성·업로드, 서명 URL 규칙, 삭제 시 렌디션 동반 제거 |
| `supabase/migrations/2026____` | `photos.renditions`, `photos.couple_id`, `couples.plan`·`photo_quota`, 쿼터 트리거 |

새 의존성은 없다. `react-native-gesture-handler`(2.32) · `react-native-reanimated`(4.5) ·
`expo-image-manipulator`(57.0)가 이미 설치돼 있다.

## 5. 검증 목표

| 목표 | 검증 방법 |
|---|---|
| 크롭 좌표 변환이 정확하다 | `npm test` — `crop.test.ts` 통과 |
| 서버 이미지 변환을 쓰지 않는다 | `src/`에서 `transform:` 사용처 0 (기존 사진 폴백 분기 제외) |
| 사진 삭제 시 고아 파일이 안 남는다 | 사진 업로드 → 삭제 후 스토리지에 `_360` 잔존 없음 |
| 쿼터가 강제된다 | 100장 도달 후 insert가 예외로 거부됨 |
| 쿼터가 상수가 아니다 | `couples.photo_quota`를 바꾸면 코드 변경 없이 한도가 바뀜 |
| 한도 도달 후에도 기존 사진이 보인다 | 쿼터 초과 상태에서 피드·캘린더·트랙 조회가 정상 동작 |
| 회귀 없음 | `npm run typecheck` + `npm test` 전부 통과 |

## 범위 밖

- **결제·구독 구현** — 스토어 IAP 연동, 영수증 검증 Edge Function, 요금제 화면, 구매 복원.
  무료 한도를 근거 있게 정하려면 베타 사용량 데이터가 필요하므로 그때 착수한다.
  이번엔 `couples.plan`·`photo_quota` 자리만 만들어 둔다
- **커플 해체·환불 시 권한 처리** — 결제와 함께 설계한다
- 스토리 만료 삭제 (영구 보관 유지로 결정)
- 오래된 사진 재압축 cron
- 기존 사진 렌디션 백필 (폴백으로 처리)
- 로컬 우선(offline-first) 저장 — 도돌이는 데이터가 전부 공유물이라 맞지 않는다(문제 항 참고)
